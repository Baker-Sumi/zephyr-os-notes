# ワークスペースの構造

## 対象範囲

上流Zephyrをmanifest repositoryとして使う標準のwest workspace（T1 topology）を扱います。自社manifestを中心にするdownstream workspace、個々のmoduleの内部実装、Gitの認証設定は扱いません。

## 前提知識

[導入手順と確認](02-導入手順と確認.md)を完了し、`west init --mr v4.4.2`と`west update`の役割を理解していることを前提にします。

## 全体像

```text
<workspace>/
├── .west/                 # westのworkspace識別と設定
│   └── config
├── .venv/                 # 任意: Python環境。manifestのprojectではない
├── zephyr/                # manifest repository。RTOS本体とwest.yml
├── modules/               # west.ymlが固定するHAL、ライブラリなど
├── tools/                 # test、simulationなどの補助project
├── bootloader/            # MCUbootなど、必要時に使うproject
└── app/                   # 開発者のアプリケーション（推奨配置の一つ）
```

この配置はディレクトリ名の慣習だけではありません。`zephyr/west.yml`の`path`が、workspace rootからの各projectの置き場所を定義します。例えば`modules/hal/*`はHAL、`modules/lib/*`は外部ライブラリ、`tools/*`は補助ツールを表します。

## ディレクトリとファイル

| パス | 入力・出力 | 責務と境界 |
| --- | --- | --- |
| `.west/config` | `west init`の出力 | workspaceを識別し、manifest repositoryへのpathを保持する。Zephyrのビルド設定ではない。 |
| `zephyr/west.yml` | Zephyr tagに含まれる入力 | remote、project、revision、path、group filterを定義するmanifest入口。 |
| `zephyr/submanifests/` | `west.yml`の`self.import`からの入力 | 上流manifestを分割する。`west update`時に解決される。 |
| `modules/` | manifest projectの出力 | Zephyrの外部依存を分類して置く。ここを一つのGitリポジトリと仮定しない。 |
| `tools/` | manifest projectの出力 | simulator、network testなどの補助projectを置く。すべての通常ビルドに必要とは限らない。 |
| `app/` | 開発者の入力 | アプリケーションのCMake、Kconfig fragment、Devicetree overlay、ソースを置く。`west.yml`を置けばdownstream manifestにもできる。 |
| `build/` | CMake configureとcompileの出力 | appとboardの組合せごとに分離する。入力ファイルではない。 |

## 処理の流れ

1. `west init`はworkspace rootに`.west/`を作り、manifest repositoryの場所を登録します。
2. 標準構成では`zephyr/west.yml`がmanifestです。`manifest.projects`の各要素がrepository URL、固定revision、workspace内pathを与えます。
3. `west update`はmanifestを解決して各projectをfetch・checkoutし、各管理projectには更新基準となる`manifest-rev`を作ります。`manifest-rev`はwestが再作成するため、開発ブランチとして使いません。
4. CMake configureはZephyr本体を起点にmoduleを検出し、appの入力、board、toolchainと合わせてbuild directoryを生成します。
5. downstreamでは、appまたは専用repositoryの`west.yml`からZephyrと必要moduleをimportできます。この場合、誰がrevisionを固定するかが上流Zephyrからdownstream manifestへ移ります。

> **注記: `modules/`は編集境界ではない**
>
> `modules/`配下は「Zephyrの付属ソース」ではなく、manifestで取得した複数の独立projectです。製品の変更は、そのmoduleのforkまたはdownstream manifestでrevisionを固定して管理します。`west update`後に直接編集しただけでは、再現可能な変更履歴になりません。

## 設定との対応

- `west.yml`の`revision`は各projectのソース版を固定し、Kconfigの`CONFIG_*`とは別の層です。
- `group-filter`は取得対象を制御します。v4.4.2の上流manifestは`babblesim`、`optional`、`testing`を既定で除外します。必要な機能が見つからない場合は、Kconfigより先にmodule groupの解決結果を確認します。
- appの`prj.conf`、`app.overlay`、`CMakeLists.txt`はworkspace topologyに依存しません。どのappをCMakeへ渡したかが、それらを選ぶ入口になります。

## 確認方法

```sh
cd <workspace>
west topdir
west manifest --resolve > manifest-resolved.yml
grep -nE '^(manifest:|  projects:|  self:|    path:|    revision:)' \
  zephyr/west.yml | head -80
git -C zephyr describe --exact-match --tags HEAD
find . -maxdepth 2 -type d \( -name .west -o -name zephyr -o -name modules -o -name tools -o -name bootloader \) -print
```

`manifest-resolved.yml`は観察用に生成する一時出力です。source treeの`west.yml`を直接書き換えず、downstreamで変更する場合は自分のmanifest repositoryに記述します。
